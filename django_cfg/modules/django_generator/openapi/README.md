# OpenAPI SDK generator

The pipeline renders one drf-spectacular document, resolves each target's
groups to OpenAPI tags, slices the document, then invokes the selected
specialist generator.

TypeScript targets use the pinned Orval tool from the frontend workspace. One
target receives one union slice; Orval's `tags-split` output keeps endpoint
modules separated by OpenAPI tag while models and runtime stay shared. The
other targets use ogen, openapi-python-client, swift-openapi-generator, buf,
or grpc-python.

## Pipeline

```
drf-spectacular → validate/fail-on-warn → spec_loader → tag resolver → slicer
                                                        → external generator
                                                        ↓
                                      staging → target.path → mirror (.tmp)
```

The generator owns group selection, slicing, content-addressed cache,
staging, contract stamps, and publication. It does not duplicate the
language-specific TypeScript generator.

## Cache and verification

```bash
DJANGO_CFG_GEN_NO_CACHE=1 make gen
python manage.py gen --check
```

The cache key includes the sliced spec, tool options, target, group set, and
output path. Every generation run invalidates target fingerprints so changes
to the Python orchestration cannot silently leave stale generated output.

Before any external generator is started, `spec_loader` applies the equivalent
of `python manage.py spectacular --validate --fail-on-warn`. This prevents
Orval, openapi-python-client, ogen, or Swift from consuming an ambiguous
contract. A project that is being migrated can temporarily set
`DJANGO_CFG_GEN_ALLOW_SCHEMA_WARNINGS=1`, but that exception should be removed
after the emitted serializer/view warnings are fixed.

## TypeScript output

What the Orval step (`tools/external/orval.py`) adds to Orval's own output:

- **Banner.** Every file Orval writes starts with `Generated by orval <version> from the django-cfg contract
  <x-cfg-contract>. Do not edit: re-run make gen.` The slice is stamped before Orval runs (`dispatch.run_single`), so
  the banner reads the real contract. The django-cfg release is left out, or every file would change on every
  release; it stays in the stamped `openapi.json` and in `runtime/cfg.ts`.
- **`runtime/cfg.ts`.** `export const CFG = { version, contract } as const`, from the stamped slice: the django-cfg
  that generated the tree and the oldest one that serves its contract. Import it from `<tree>/runtime/cfg`.
- **Consumer `package.json`.** Orval reads the nearest `package.json` above the folder the tree is published to, for
  the TypeScript, TanStack Query, Zod and Faker versions. `override.query.version: 5` stays for consumers that
  declare no `@tanstack/react-query` there.
- **Formatting.** prettier formats the tree with the config a file in the consumer folder gets (`resolveConfig` on the
  consumer path, `.editorconfig` ignored), using the workspace's prettier or else Orval's. Orval's `formatter` option
  is not used: it takes the config of where it writes, and with `source_root` that is the Django project.
- **Mutator shim.** `runtime/orval-mutator.ts` is generated as a two-parameter wrapper around the runtime's
  `djangoFetch`, with literal `export type ErrorType<_Error> = ApiClientError` and `BodyType`. Orval reads that file
  as text, so operations take `options?: DjangoRequestInit`, every query and mutation hook takes `request` (and
  passes it), and `TError` is `ApiClientError`. A re-export would count as one parameter and give `RequestInit`, no
  `request` and `TError = unknown`. Where the shim imports from:
  - `@djangocfg/api` by default;
  - a hand-written `runtime/orval-mutator.ts` in an ancestor of the tree, for `djangoFetch` and `DjangoRequestInit`
    (`ApiClientError` still comes from `@djangocfg/api`). Use it only for a real exception, such as a package that
    sets its own origin;
  - inside `@djangocfg/api` itself, its `runtime` folder, relatively (a package cannot import itself by name).

- **Request flags.** `orval.request_option_overrides` builds Orval `override.operations` and `override.tags` from the
  sliced spec. Orval inlines each `requestOptions` into the call before the caller's options
  (`djangoFetch(url, { auth: 'none', ...options, method, … })`), so a caller can still override a flag, and merges a
  tag's flags with an operation's. The runtime acts on them (`DjangoRequestInit`):
  - `auth: 'none'` when the operation takes no credentials: `security` is `[{}]` or `[]`, or absent while the
    document has no `security` (an absent one inherits the document's). Optional auth (`[{jwt: []}, {}]`) gets no
    flag. No Bearer is sent, no refresh is tried, and a 401 never expires the session;
  - `skipAuthRefresh: true` on a sign-in step, which its view marks with
    `extend_schema(extensions=SIGN_IN_STEP)` (`django_cfg.core.contract`, `x-cfg-auth: sign-in`). django-cfg marks
    password login, OTP request and verify, the OAuth callbacks and the 2FA verify steps. Any other value stops
    generation and names the operation;
  - `origin: 'direct'` for every operation of a tag listed in the Target's `direct_origin_tags`.

- **Realtime refresh.** A GET marked `@invalidated_by(...)` (`x-realtime-invalidates`) gets Orval's per-operation
  `query.queryOptions` mutator, `runtime/realtime-query.ts`, generated from the slice. Orval calls it with the query
  options, the call's own arguments (`{ id }`, `{ params }`) and the `operationId`. It adds the concrete topic names
  to `meta.realtimeTopics` and keeps the caller's `meta`. `@djangocfg/layouts` (`BaseApp`) watches the QueryCache:
  while such a query has an observer its topics stay subscribed, and a message or a gap invalidates it. A pattern
  parameter (`orders:{order_id}`) is filled from the path parameter of the same name, under Orval's camel-case name
  for it (`orderId`). One that is no path parameter of the operation stops generation, named. Other operations and
  non-GET ones are left as they were. See `tools/realtime/query_topics.py` for why a mutator and not
  `override.query.options` (deprecated, static) or a map the app hands to the layout.

### Target options

TypeScript targets accept these fields on `Target` (`public/config.py`). They are refused on other languages, and a
target that sets none keeps exactly the output it had.

| Option | Default | Effect |
|---|---|---|
| `auth_mode` | `"default"` | `"public"`: the generated shim sends every request with `auth: 'none'`, after the caller's options, so no call carries the session. For a client of public endpoints only. |
| `direct_origin_tags` | `[]` | Raw OpenAPI tags whose operations go to the API host (`origin: 'direct'`), never through the proxy. A tag that no operation of the target carries stops generation. |
| `infinite` | `False` | `override.query.useInfinite` with `useInfiniteQueryParam: ['page', 'cursor']`: `use<Op>Infinite` and `get<Op>InfiniteQueryOptions` for every GET that takes a `page` (else `cursor`) query parameter; Orval skips the other GETs. Orval generates no `getNextPageParam`: spread the runtime's `drfPageParams` (page numbers) or `drfCursorParams` (cursors) into `query`. Infinite keys start with `'infinite'`, so a mutation must invalidate `get<Op>InfiniteQueryKey(...)` too. |

The golden snapshot `tests/integration/test_orval_snapshot.py` runs this step on a committed slice and compares every
file. After an intended change, refresh it with `UPDATE_SNAPSHOTS=1` (command in the test's docstring) and review the
diff.

## TypeScript type-check gate

A TypeScript tree is published only if it type-checks. After Orval writes a target, and before the tree replaces
its consumer folder, the pipeline runs `tsc --noEmit` on it (`pipeline/runner/typecheck.py`,
`tools/external/tsc.py`):

- The tree is checked as if it were already in its final folder, from a temporary sibling copy
  (`.<name>.djcfg-tsc-<id>`). Its imports therefore resolve as they will for the consumer: the runtime shim, the
  consumer's `node_modules` and `@djangocfg/api`.
- It uses the consumer's TypeScript (the nearest `node_modules/typescript`) and extends the nearest
  `tsconfig.json`. Only the input list and the emit options are overridden.
- An error in a generated file fails the target, and so does an error with no location (a broken config). The
  consumer folder keeps its previous tree and `manage.py gen` exits non-zero with up to 20 diagnostics. Errors in
  imported handwritten files, such as the runtime, do not fail generation. A runtime that stops exporting what
  the shim imports does fail it, because tsc reports that error in the shim.
- Missing TypeScript or node is a failure, not a skip.

Opt-out for one run:

```bash
DJANGO_CFG_GEN_SKIP_TYPECHECK=1 make gen
```

Use it only when the check cannot run for a reason outside the tree. For example, a target whose shim imports
`@djangocfg/api` needs that package's built `dist` types, which a fresh checkout does not have yet. Every target
skipped this way prints a `type-check skipped` line. The same command is how to inspect a tree that fails: generate
it with the gate off, then run the consumer's own `tsc --noEmit`.

The generated client's behaviour (origin, headers, refresh, soft Zod) is covered separately by the smoke suite in
`solution/frontend/packages/api/smoke/`. `make test-fast` runs it through
`django_generator/tests/integration/test_generated_client_smoke.py`.

## Schema discipline

Generation stops, naming the route (and the view, resolved through the URLconf) and the fix, on:

- an **operationId collision**: drf-spectacular would rename all but the first with `_2`, `_3` in URL order and
  only warn, so client names would depend on route order (`spec_loader`, refused even with the warning escape hatch);
- an Orval operation **without a response schema**: no success response, or a `2xx` media type without `schema`.
  Orval would type it `unknown`, or refuse the spec without naming the view. A `2xx` without content is an empty
  body (`void`) and is fine (`postprocess.enforce_response_schemas`);
- an **unknown group**: a `Target.groups` entry that is not an `OpenAPIGroupConfig` and is no tag of any operation
  or topic. It used to give an empty client. A configured group whose views carry no tag yet still slices to nothing.

Every operation should have stable `operationId` and explicit OpenAPI tags.
Use named serializers for reusable request/response shapes and
`@extend_schema(request=None)` for no-body actions. The resulting schema is
the source of truth for Orval's TypeScript types, Zod schemas, React Query
operations, and MSW mocks.

The former Hey API/`ts_extras` implementation is retained only under
`django_generator/.archive/` for historical reference; it is not imported by
the active pipeline.
