# OpenAPI SDK generator

The pipeline renders one drf-spectacular document, resolves each target's groups to OpenAPI tags, slices the
document, then runs the target's generator. TypeScript targets use the pinned Orval (8.48.0) from the frontend
workspace. The other languages use ogen, openapi-python-client, swift-openapi-generator, buf or grpc-python.

This page says what a TypeScript tree contains and which options shape it. Changing the generator itself:
[`../@docs/openapi/`](../@docs/openapi/README.md).

## Pipeline

```
1. drf-spectacular → validate (--fail-on-warn) → normalize            spec_loader, postprocess
2. per target: groups → tags → slice → stamp → request flags, topics  dispatch, slicer, stamp, orval.py
3. Orval: operations, React Query v5 hooks, Zod, MSW; then prettier   tools/external/orval.py
4. tsc --noEmit on the staged tree → git guard → swap                 runner/typecheck.py, tools/external/tsc.py
5. runtime @djangocfg/api honours the flags                           solution/frontend/packages/api/src/runtime
6. BaseApp: QueryClient, realtime invalidation through the QueryCache @djangocfg/layouts
```

The generator owns group selection, slicing, the content-addressed caches, staging, contract stamps and publication.
It does not duplicate what Orval generates.

## A TypeScript tree

```
<Target.path>/
  endpoints/<tag>/<tag>.ts        operations, hooks, query keys     (Orval)
  endpoints/<tag>/<tag>.msw.ts    MSW handlers, Faker factories     (Orval, mock: true)
  models/*.zod.ts                 Zod schemas and their types       (Orval)
  runtime/orval-mutator.ts        the mutator shim                  (generated by django-cfg)
  runtime/cfg.ts                  CFG = { version, contract }       (generated by django-cfg)
  runtime/realtime-query.ts       meta.realtimeTopics mutator       (only when a GET is invalidated_by a topic)
  realtime.ts                     typed topic builders              (only when the slice has x-realtime)
  openapi.json                    the stamped slice
```

What django-cfg adds to Orval's own output:

- **Banner.** Every file Orval writes starts with `Generated by orval <version> from the django-cfg contract
  <x-cfg-contract>. Do not edit: re-run make gen.` The slice is stamped before Orval runs (`dispatch.run_single`), so
  the banner reads the real contract. The django-cfg release is left out, or every file would change on every
  release; it stays in `openapi.json` and `runtime/cfg.ts`.
- **`runtime/cfg.ts`.** `export const CFG = { version, contract } as const`: the django-cfg that generated the tree and
  the oldest one that serves its contract.
- **Consumer `package.json`.** Orval reads the nearest `package.json` above the folder the tree is published to, for
  the TypeScript, TanStack Query, Zod and Faker versions. `override.query.version: 5` stays for consumers that
  declare no `@tanstack/react-query` there.
- **Formatting.** prettier formats the tree with the config a file in the consumer folder gets (`resolveConfig` on the
  consumer path, `.editorconfig` ignored), using the workspace's prettier or else Orval's. Orval's `formatter` option
  is not used: it takes the config of where it writes, and with `source_root` that is the Django project.
- **Mutator shim.** `runtime/orval-mutator.ts` is a two-parameter wrapper around the runtime's `djangoFetch`, with
  literal `export type ErrorType<_Error> = ApiClientError` and `BodyType`. Orval reads that file as text, so
  operations take `options?: DjangoRequestInit`, every query and mutation hook takes `request` (and passes it), and
  `TError` is `ApiClientError`. Where the shim imports from (`dispatch.runtime_import_for`):
  - `@djangocfg/api` by default;
  - a hand-written `runtime/orval-mutator.ts` in an ancestor of the tree, for `djangoFetch` and `DjangoRequestInit`
    (`ApiClientError` still comes from `@djangocfg/api`). Use it only for a real exception;
  - inside `@djangocfg/api` itself, its `runtime` folder, relatively (a package cannot import itself by name).

### Request flags

`orval.request_option_overrides` builds Orval `override.operations` and `override.tags` from the sliced spec. Orval
inlines each `requestOptions` into the call before the caller's options (`djangoFetch(url, { auth: 'none',
...options, method, … })`), so a caller can still override a flag, and merges a tag's flags with an operation's. The
runtime acts on them (`DjangoRequestInit`):

- `auth: 'none'` when the operation takes no credentials: `security` is `[{}]` or `[]`, or absent while the document
  has no `security` (an absent one inherits the document's). Optional auth (`[{jwt: []}, {}]`) gets no flag. No Bearer
  is sent, no refresh is tried, and a 401 never expires the session;
- `skipAuthRefresh: true` on a sign-in step, which its view marks with `extend_schema(extensions=SIGN_IN_STEP)`
  (`django_cfg.core.contract`, `x-cfg-auth: sign-in`). django-cfg marks password login, OTP request and verify, the
  OAuth callbacks and the 2FA verify steps. Any other value stops generation and names the operation;
- `origin: 'direct'` for every operation of a tag listed in the Target's `direct_origin_tags`.

### Realtime refresh

A GET marked `@invalidated_by(...)` (`x-realtime-invalidates`) gets Orval's per-operation `query.queryOptions`
mutator, `runtime/realtime-query.ts`, generated from the slice. Orval calls it with the query options, the call's own
arguments (`{ id }`, `{ params }`) and the `operationId`. It adds the concrete topic names to `meta.realtimeTopics`
and keeps the caller's `meta`. `BaseApp` watches the QueryCache: while such a query has an observer its topics stay
subscribed, and a message or a gap invalidates it.

A pattern parameter (`orders:{order_id}`) is filled from the path parameter of the same name, under Orval's
camel-case name (`orderId`). One that is no path parameter of the operation stops generation, named. Other operations
and non-GET ones are left as they were. Because of the mutator, the options factory of such an operation is a hook,
`use<Op>QueryOptions`, not `get<Op>QueryOptions`. Why a mutator and not `override.query.options` or a map handed to
the layout: `tools/realtime/query_topics.py`.

## Target options

TypeScript targets accept these fields on `Target` (`public/config.py`). They are refused on other languages, and a
target that sets none keeps exactly the output it had.

| Option | Default | Effect |
|---|---|---|
| `auth_mode` | `"default"` | `"public"`: the generated shim sends every request with `auth: 'none'`, after the caller's options, so no call carries the session. For a client of public endpoints only. |
| `direct_origin_tags` | `[]` | Raw OpenAPI tags whose operations go to the API host (`origin: 'direct'`), never through the proxy. A tag that no operation of the target carries stops generation. |
| `infinite` | `False` | `override.query.useInfinite` with `useInfiniteQueryParam: ['page', 'cursor']`: `use<Op>Infinite` and `get<Op>InfiniteQueryOptions` for every GET that takes a `page` (else `cursor`) query parameter; Orval skips the other GETs. Orval generates no `getNextPageParam`: spread the runtime's `drfPageParams` (page numbers) or `drfCursorParams` (cursors) into `query`. Infinite keys start with `'infinite'`, so a mutation must invalidate `get<Op>InfiniteQueryKey(...)` too. |

`mock` (MSW handlers) and `prettier` (the prettier pass) are pipeline options of `GenerationTarget.options`, read by
`dispatch._dispatch_tool` and on by default. They are not `Target` fields, and an unknown `Target` keyword is ignored,
so `Target(mock=False)` changes nothing. Adding an option: [`../@docs/openapi/extending.md`](../@docs/openapi/extending.md).

## Gates

- **Golden snapshot.** `tests/integration/test_orval_snapshot.py` runs this step on a committed slice and compares
  every file. After an intended change, refresh it with `UPDATE_SNAPSHOTS=1` and review the diff.
- **Type-check gate.** A TypeScript tree is published only if `tsc --noEmit` passes on it, checked from a temporary
  sibling of its final folder, with the consumer's TypeScript and nearest `tsconfig.json`. An error in a generated
  file fails the target and the consumer keeps its previous tree. Opt-out for one run, only for a reason outside the
  tree: `DJANGO_CFG_GEN_SKIP_TYPECHECK=1 make gen`.
- **Smoke suite.** `solution/frontend/packages/api/smoke/` calls a generated group with `fetch` stubbed: origin,
  headers, refresh, soft Zod. `make test-fast` runs it through `tests/integration/test_generated_client_smoke.py`.

Commands and details: [`../@docs/openapi/testing.md`](../@docs/openapi/testing.md).

## Cache and verification

```bash
DJANGO_CFG_GEN_NO_CACHE=1 make gen
python manage.py gen --check
```

The cache key includes the sliced spec, tool options, target, group set and output path.

## Schema discipline

Before any generator runs, `spec_loader` applies the equivalent of `manage.py spectacular --validate --fail-on-warn`.
A project being migrated can set `DJANGO_CFG_GEN_ALLOW_SCHEMA_WARNINGS=1` for a while; remove it once the warnings are
fixed.

Generation also stops, naming the route (and the view, resolved through the URLconf) and the fix, on:

- an **operationId collision**: drf-spectacular would rename all but the first with `_2`, `_3` in URL order and only
  warn, so client names would depend on route order (refused even with the warning escape hatch);
- an Orval operation **without a response schema**: no success response, or a `2xx` media type without `schema`. A
  `2xx` without content is an empty body (`void`) and is fine (`postprocess.enforce_response_schemas`);
- an **unknown group**: a `Target.groups` entry that is not an `OpenAPIGroupConfig` and is no tag of any operation or
  topic. A configured group whose views carry no tag yet still slices to nothing.

Every operation should have a stable `operationId` and explicit tags. Use named serializers for reusable shapes and
`@extend_schema(request=None)` for no-body actions.

The former hey-api / `ts_extras` implementation is kept only under `django_generator/.archive/` and is not imported by
the active pipeline.
