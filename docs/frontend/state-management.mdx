# State Management

Start with Context + React Query v5. Add Zustand only when you have complex
client-only state with frequent updates, undo/redo, or cross-component
synchronization.

<Callout type="info">
For Zustand store patterns, persistence, and undo/redo see [Zustand recipe](./recipes/zustand). For generated operations and query keys see [Data Layer](./data-layer).
</Callout>

## The QueryClient

`BaseApp` from `@djangocfg/layouts` provides the app's one QueryClient. Do not
add a `QueryClientProvider` of your own, and never create a QueryClient at
module scope: on the server it would share one cache between requests.

`BaseApp` picks the client in this order:

1. the `queryClient` prop, used as it is (its defaults are not merged);
2. a QueryClient already provided above `BaseApp`, reused, never nested;
3. otherwise a new one per mount from `createAppQueryClient()`.

| Default | Value |
|---------|-------|
| Query retry | none on a 4xx; up to 2 on a network error or a 5xx |
| `throwOnError` | `false` |
| `staleTime` | 30 s |
| Refetch on window focus | on |
| Mutation retry | none |

```tsx
import { BaseApp, createAppQueryClient } from '@djangocfg/layouts';

// Only when the app needs its own defaults. Create it inside the component.
const [queryClient] = useState(() => createAppQueryClient());

<BaseApp
  queryClient={queryClient}
  queryDevtools={() => import('@tanstack/react-query-devtools')}
>
  {children}
</BaseApp>
```

`queryDevtools` is optional. It renders only in development and loads lazily,
and the app installs `@tanstack/react-query-devtools` itself.

`@tanstack/react-query` is a peer dependency of `@djangocfg/layouts`, so every
app that mounts `BaseApp` lists it as a direct dependency. A QueryClient passed
explicitly to a generated hook is a second cache: the realtime bridge never
sees it, so invalidations from Centrifugo do not reach it.

## Context Architecture

### Standard Context Template

Every context follows this pattern. The example uses the demo app's coin
endpoints (`/apix/crypto/coins/`):

```tsx
'use client';
import { createContext, useCallback, useContext, useMemo } from 'react';
import type { ReactNode } from 'react';
import { useQueryClient } from '@tanstack/react-query';
import {
  getCryptoCoinsListQueryKey,
  useCryptoCoinsCreate,
  useCryptoCoinsDestroy,
  useCryptoCoinsList,
} from '@api/generated/endpoints';
import type {
  CoinListing,
  CoinListingWrite,
  CoinListingWriteRequest,
  CryptoCoinsListParams,
} from '@api/generated/models';

interface CoinsContextType {
  coins: CoinListing[];
  isLoading: boolean;
  error: string | null;
  refresh: () => Promise<void>;
  createCoin: (data: CoinListingWriteRequest) => Promise<CoinListingWrite>;
  deleteCoin: (id: number) => Promise<void>;
}

const CoinsContext = createContext<CoinsContextType | undefined>(undefined);

export function CoinsProvider({
  params,
  children,
}: {
  params?: CryptoCoinsListParams;
  children: ReactNode;
}) {
  // 1. Generated React Query v5 query (the QueryClient comes from BaseApp)
  const queryClient = useQueryClient();
  const { data, error, isPending } = useCryptoCoinsList(params, {
    query: { staleTime: 60_000 },
  });

  // 2. Derived data with useMemo
  const coins = useMemo(() => data?.results ?? [], [data]);

  // 3. Mutation hooks
  const createMutation = useCryptoCoinsCreate();
  const destroyMutation = useCryptoCoinsDestroy();

  // 4. Stable action callbacks; invalidate with the generated key factory
  const refresh = useCallback(
    () => queryClient.invalidateQueries({ queryKey: getCryptoCoinsListQueryKey(params) }),
    [queryClient, params],
  );
  const createCoin = useCallback(async (body: CoinListingWriteRequest) => {
    const created = await createMutation.mutateAsync({ data: body });
    await refresh();
    return created;
  }, [createMutation, refresh]);
  const deleteCoin = useCallback(async (id: number) => {
    await destroyMutation.mutateAsync({ id });
    await refresh();
  }, [destroyMutation, refresh]);

  // 5. Memoized context value. A generated hook's error is typed `unknown`.
  const value = useMemo<CoinsContextType>(() => ({
    coins,
    isLoading: isPending,
    error: error instanceof Error ? error.message : null,
    refresh,
    createCoin,
    deleteCoin,
  }), [coins, isPending, error, refresh, createCoin, deleteCoin]);

  return <CoinsContext.Provider value={value}>{children}</CoinsContext.Provider>;
}

// 6. Guard hook
export function useCoins(): CoinsContextType {
  const context = useContext(CoinsContext);
  if (!context) throw new Error('useCoins must be used within CoinsProvider');
  return context;
}
```

The six steps: generated query, `useMemo` derived data, mutation hooks,
`useCallback` actions, memoized value, and a guard hook that throws if used
outside the provider.

### Provider Composition

Small apps use manual nesting in a layout or `AppProvider`:

```typescript
// AppProvider.tsx (cmdop/my — 9 providers)
export function AppProvider({ children }) {
  return (
    <WorkspacesProvider>
      <MachinesProvider>
        <PersonalMachineProvider>
          <SchedulesProvider>
            <SkillsProvider>
              <ActivityProvider>
                <SystemProvider>
                  <BalanceProvider>
                    <TerminalProvider>
                      {children}
                    </TerminalProvider>
                  </BalanceProvider>
                </SystemProvider>
              </ActivityProvider>
            </SkillsProvider>
          </SchedulesProvider>
        </PersonalMachineProvider>
      </MachinesProvider>
    </WorkspacesProvider>
  );
}
```

Large apps use `composeProviders()` to avoid deep nesting:

```typescript
export function composeProviders(providers: ProviderEntry[]): React.FC<{ children: ReactNode }> {
  return function ComposedProviders({ children }) {
    return providers.reduceRight<ReactNode>((acc, entry) => {
      if (Array.isArray(entry)) {
        const [Provider, props] = entry;
        return <Provider {...props}>{acc}</Provider>;
      }
      return <entry>{acc}</entry>;
    }, children);
  };
}

// Usage: split into API layer + UI layer
const APIProviders = composeProviders(createAPIProviders(projectId));
const UIProviders = composeProviders(UI_PROVIDERS);
```

### Context Decomposition

Each context has a single responsibility. No god-contexts:

```
CatalogProvider
  └── FiltersProvider        (URL state → API params)
        └── VehiclesProvider (React Query data + hydration)
              └── FavoritesProvider  (localStorage, max 100)
                    └── RecentlyViewedProvider  (localStorage, max 20)
```

## URL-First Filter State

Filters live in URL search params. No Zustand, no `useState` for filters:

```typescript
// FiltersContext.tsx
const searchParams = useSearchParams();
const [isPending, startTransition] = useTransition();

const filters = useMemo(() => parseURLFilters(searchParams), [searchParams]);

const setFilter = useCallback(<K extends keyof FilterState>(
  key: K, value: FilterState[K]
) => {
  const newFilters = { ...filters, [key]: value };
  if (key !== 'page') newFilters.page = 1;  // Reset page on filter change
  startTransition(() => {
    router.push(buildURLFromFilters(newFilters));
  });
}, [filters, router]);
```

Benefits: shareable URLs, browser back/forward works, SSR-compatible.

## When to Use What

| Tool | When | Example |
|------|------|---------|
| React Query + Context | Server data with CRUD actions | Vehicles list, machines, workspaces |
| URL state (`useSearchParams`) | Filters, pagination, sorting | Catalog filters, search queries |
| `useLocalStorage` | Persistent local preferences | Favorites, recently viewed, workspace ID |
| Zustand | Complex client-only state, high-frequency updates | Video editor, canvas, timeline |
| Event bus | Cross-component dialog triggers | Open dialog from unrelated component |

## localStorage-Backed State

For persistent local preferences without Zustand:

```typescript
// Uses useLocalStorage from @djangocfg/ui-core/hooks
const [favorites, setFavorites] = useLocalStorage<string[]>('favorites', []);
const [recentlyViewed, setRecentlyViewed] = useLocalStorage<ViewedItem[]>('recently_viewed', []);
const [currentWorkspaceId, setCurrentWorkspaceId] = useLocalStorage<string | null>('workspace_id', null);
```

Keys follow `<owner>.<area>.<name>`. A bare name such as `'favorites'` is stored as
`cfg.ui.favorites`; wrap the app in `<StorageNamespaceProvider owner="myapp">` to get
`myapp.ui.favorites`, or pass a full key (`'myapp.catalog.favorites'`) to name the area yourself.
`createStorageNamespace('myapp')` provides `key()`, `keys()` and `clear()` for a settings reset.

## Event Bus

For decoupled dialog communication between unrelated components:

```typescript
// _lib/events/machines.ts
import { events } from '@djangocfg/ui-core/hooks';
export const emitOpenMachineInfoDialog = (payload) =>
  events.publish({ type: 'OPEN_MACHINE_INFO_DIALOG', payload });

// In the dialog host component:
events.subscribe('OPEN_MACHINE_INFO_DIALOG', (payload) => setOpen(true));
```

## Rules

1. Start with Context + React Query v5 — add Zustand only when you need complex client-only state with frequent updates or undo/redo
2. Follow the 6-step context template: generated query → `useMemo` → mutation hooks → `useCallback` actions → memoized value → guard hook
3. Use `composeProviders()` when you have more than ~10 providers to avoid deep nesting
4. Filters live in URL search params (`useSearchParams`) — never in `useState` or Zustand
5. Each context has a single responsibility — decompose into a provider chain instead of creating a god-context
6. Use `useLocalStorage` for persistent client preferences — only reach for Zustand `persist` when you also need middleware (devtools, undo)
