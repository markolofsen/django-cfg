# Data Layer

The data layer is generated from Django ViewSets via a validated OpenAPI
contract. The pinned Orval target emits operations, React Query v5 hooks/query
keys, Zod schemas, and MSW handlers. The application-owned runtime boundary
handles authentication, refresh, transport, and normalized errors.

<Callout type="info">
For Django ViewSet patterns see [App Design Guide — ViewSets](../guides/app-design/viewsets). For SSR data fetching see [SSR & Hydration](./ssr-hydration).
</Callout>

## Generation Pipeline

```
Django ViewSets
  → drf-spectacular → OpenAPI schema
    → python manage.py gen
      → app/_lib/api/generated/<domain>/
```

A generated target (the `path` of a `Target` in `generation.py`) contains:

```
generated/
├── endpoints/              # Orval tags-split operations and hooks
├── models/                 # TypeScript and Zod schemas
├── mocks/                  # MSW handlers
└── index.ts                # Stable project barrel
```

<Callout type="warning">
Never edit `generated/` manually. Regenerate with `python manage.py gen`.
</Callout>

## Runtime boundary

Generated operations use the shared runtime/mutator boundary from
`@djangocfg/api`. Application code does not create a second API client or token
store:

```typescript
import { auth, djangoFetch } from '@djangocfg/api';

export { auth, djangoFetch };
```

The generated `runtime/orval-mutator.ts` re-exports this boundary. It adds auth
headers, refresh/retry behavior, normalized errors, and Zod response parsing.
For SSR, use the imperative operation or its generated query options; do not
instantiate a browser client in a Server Component.

```typescript
import { cryptoCoinsList } from '@api/generated/endpoints';

const coins = await cryptoCoinsList({ page: 1 });
```

## Zod Validation

Generated operations validate every response at runtime:

```typescript
// Orval operation; the schema is passed to djangoFetch by generated code.
const response = await cryptoCoinsList({ page: 1 });
// response is already Zod-validated
```

On validation failure, a `CustomEvent('zod-validation-error', ...)` is dispatched to the browser window for dev tooling.

## React Query Hooks and Query Keys

Generated hooks wrap operations with TanStack Query:

```typescript
import { useQueryClient } from '@tanstack/react-query';
import {
  useCryptoCoinsList,
  getCryptoCoinsListQueryKey,
} from '@api/generated/endpoints';

const queryClient = useQueryClient();
const query = useCryptoCoinsList({ page: 1 }, {
  query: { staleTime: 60_000 },
});

queryClient.invalidateQueries({
  queryKey: getCryptoCoinsListQueryKey({ page: 1 }),
});
```

Use the generated `enabled` option to conditionally skip fetching. After a
mutation, invalidate the generated query key with `queryClient`; never hand-build
or globally mutate string-based cache keys.

## Type Re-Export Pattern (types.ts)

Components import types from the context's `types.ts`, never from `generated/` directly:

```typescript
// contexts/<domain>/types.ts — SINGLE SOURCE OF TRUTH
import { CoinListing } from '@api/generated/models';

// Re-export from the generated model barrel, not a disposable file path.
export { CoinListing } from '@api/generated/models';
export type { CoinListingOutput } from '@api/generated/models';

// App-specific types stay handwritten.
export type CatalogItem = CoinListing;

// App-specific types
export interface FilterState {
  brand: string | null;
  source: string | null;
  minPrice: number | null;
  maxPrice: number | null;
  page: number;
  pageSize: number;
}
```

The dual export pattern (`export const` + `export type` for the same name) allows both runtime usage and type-level usage from a single import.

## Query configuration

Configure TanStack Query once at the application boundary and keep endpoint
freshness close to the generated hook:

| Option | Use Case | Guidance |
|--------|----------|----------|
| `staleTime` | Reference/static data | Avoid unnecessary refetches |
| `gcTime` | Inactive data | Bound retained cache lifetime |
| `enabled` | Conditional queries | Wait for required input |

The provider owns retry and focus policies; generated query keys own cache identity.

## CFG API vs Custom API

Two tiers of API clients:

| Tier | Package | Scope |
|------|---------|-------|
| CFG API | `@djangocfg/api` | Universal: accounts, auth, JWT, 2FA |
| Custom API | `generated/` per app | App-specific: catalog, projects, terminals |

Extensions use `createExtensionAPI()` from `@djangocfg/ext-base` to share auth storage with the core API client. See [Extensions recipe](./recipes/extensions).

## Auth token & logging

The `@djangocfg/api` runtime boundary handles tokens, headers, refresh, and
normalized errors for generated operations. One behavior worth knowing:

- **Role-aware console logging.** All `@djangocfg/*` loggers share a runtime level
  (`applyRoleLogPolicy` / `setLogLevel` from `@djangocfg/api`). `AuthProvider`
  applies it automatically: admins (and dev) get debug logs, regular users in
  production get a clean console (errors only). Errors still reach
  `@djangocfg/devtools` regardless.

## Rules

1. Never edit `generated/` directories — regenerate with `python manage.py gen`.
2. Import from `generated/endpoints`, `generated/models`, or an app-owned API barrel; do not couple application code to disposable operation files.
3. Use generated query-key factories for cache reads and invalidation.
4. Keep authentication, refresh, error normalization, and transport in the runtime boundary.
5. Use `enabled` for conditional queries; never call hooks conditionally.
