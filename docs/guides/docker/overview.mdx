# Docker Setup Overview

This guide describes the Docker setup that ships in the django-cfg repository
(`projects/docker/`). It is the setup that runs the project's own sites, and a
reasonable pattern to copy for your own project. It is not a generic recipe: where
your project differs (its own images, host, proxy), your project's deployment notes
win.

<Callout type="info">
Everything below was read from the compose files and Dockerfiles in
`projects/docker/`. If a file and this page disagree, the file is right.
</Callout>

## What runs

The production layout is one compose file per **group**, all with project name
`djangocfg`, joined by an orchestrator file:

```mermaid
graph TB
    T[Traefik - routes by label] --> A[api - Django, uvicorn]
    T --> S[storybook]
    T --> D[demo]
    A --> P[(shared PostgreSQL)]
    A --> R[(Redis)]
    W[rq-worker] --> P
    W --> R
    C[rq-scheduler] --> R
    X[resetter - profile demo-reset] -. docker.sock .-> A
```

| Group file | Services | Public host | Container port |
|---|---|---|---|
| `docker-compose-prod.django.yaml` | `api`, `rq-worker`, `rq-scheduler` (`grpc` is commented out) | `api.djangocfg.com` | 8000 |
| `docker-compose-prod.storybook.yaml` | `storybook` | `ui.djangocfg.com` | 3781 |
| `docker-compose-prod.demo.yaml` | `demo` (Next.js example) | `demo.djangocfg.com` | 3010 |
| `docker-compose-prod.extras.yaml` | `resetter`, only under the `demo-reset` profile | none | none |
| `docker-compose-prod.docs.yaml` | `docs` (Nextra site) | `djangocfg.com` | 3778 |
| `docker-compose-prod.yaml` | orchestrator: `include`s django, extras, storybook and demo (not docs) | | |

Facts that are easy to get wrong:

- **There is no Traefik, PostgreSQL or Redis service in the production files.**
  Every group attaches to the external network `dokploy-network`, where the host's
  Traefik reads the container labels, and the Django container expects a PostgreSQL
  host (taken from `DATABASE__URL`) and a host named `redis` on that network. The
  database is a shared one (`make createdb` runs against the container
  `shared-db-postgres`).
- **There is no WebSocket service.** No WebSocket transport ships in the package
  (the Centrifugo integration was removed in 2.3.0).
- **gRPC is off.** The `grpc` service is kept commented out in the production group;
  the monolithic `docker-compose.yaml` and the local file still define it.
- **The worker and scheduler reuse the API image.** Only `api` has a `build:`
  section; `rq-worker` and `rq-scheduler` use `djangocfg-api:latest` with another
  `command` (`python manage.py rqworker high default low knowledge` and
  `python manage.py rqscheduler`).
- **Django is served by uvicorn** (ASGI, 4 workers) on port 8000, health-checked at
  `/healthz/ready`.

## Four compose layouts

| File | Use |
|---|---|
| `docker-compose-prod.*.yaml` | Production, one group at a time or all through `docker-compose-prod.yaml`. See [Production](./production). |
| `docker-compose.yaml` | The same API services in a single file (API, worker, scheduler, gRPC, resetter). Older monolithic form of the Django group. |
| `docker-compose-local.yaml` | Local stack with its own Traefik, `pgvector/pgvector:pg15`, Redis 7, Django and gRPC. See [Development](./development). |
| `docker-compose-local-services.yml` | Only Redis, an RQ worker and an RQ scheduler, for running Django on the host. |

## The directory

```
projects/docker/
  Makefile                              # every command, `make help`
  .env.example                          # template for .env.local / .env.prod
  .env.local  .env.prod                 # env files the compose files read
  docker-compose*.y*ml                  # see the tables above
  services/
    django/Dockerfile, entrypoint.sh    # the API image (api, worker, scheduler, grpc)
    frontend/Dockerfile                 # docs (build args APP_NAME, APP_DIR, APP_PORT)
    frontend/Dockerfile.storybook       # storybook
    frontend/Dockerfile.demo            # demo
    demo-resetter/                      # db-reset.sh + a docker:27-cli image
    postgres/init.sql                   # extensions and the mcp_docs database
```

## Commands

Run from `projects/docker`. `make help` lists all of them.

```bash
make deploy-prod        # createdb, build the django group, start it, wait healthy, migrate
make deploy-django      # build, start, wait healthy, migrate (no createdb)
make storybook-deploy   # build + start storybook
make appdemo-deploy     # build + start the demo
make docs-deploy        # build + start docs
make status-all         # status of the services
make logs-django        # logs of the django group
make shell              # Django shell in djangocfg-api
```

`NO_CACHE=1 make build-django` builds without the layer cache. The `demo-*` targets
(no `app` prefix) belong to an older public-mirror deployment, not to the demo
described here.
