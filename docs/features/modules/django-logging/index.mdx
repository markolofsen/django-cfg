# Django Logging

Django-CFG logs the Django / 12-factor way: **records go to stdout/stderr and the platform routes them** (Docker, systemd, your terminal). The app does not manage log files unless you ask for one. Importing `django_cfg` creates no directories, writes no files and does not touch your root handlers.

## Features

- **stdout by default** — no `logs/` folder in the project tree
- **File is opt-in** — `DJANGO_CFG_LOG_DIR` or `DjangoConfig(logging=...)`; size-rotated with a bounded backup count, safe with several workers, and pruned at boot
- **JSON off a terminal** — one object per line when stderr is not a terminal (a container, systemd, a pipe), text at your terminal; `DJANGO_CFG_LOG_FORMAT` overrides
- **Your `LOGGING` wins** — django-cfg only generates the `LOGGING` dict; override it in the project as usual
- **Sanitized extra context** — reserved `LogRecord` attributes in `extra={}` are prefixed with `ctx_`

## Quick Start

django-cfg has no logger wrapper. Use the standard library:

```python
import logging

logger = logging.getLogger(__name__)

logger.debug("Processing started")
logger.info("User created", extra={"user_id": 42})
logger.warning("Rate limit approaching", extra={"endpoint": "/api/users"})
logger.error("Payment failed", extra={"order_id": "ORD-123"})
```

Loggers named under `django_cfg` (every django-cfg module uses `__name__`) get the handlers and level from the generated `LOGGING` dict; your own loggers follow your project's `LOGGING`.

<Callout type="warning">
**Migration:** `get_logger` (from `django_cfg`, `django_cfg.utils` and `django_cfg.modules.django_logging`) and `DjangoLogger` were removed with no alias. Replace `get_logger(name)` with `logging.getLogger(name)` (or `logging.getLogger(__name__)`) and drop the import. The old helper rewrote short names to `django_cfg.<path>`; a plain name is now used as given.
</Callout>

## Where logs go

django-cfg decides this itself; a project that sets nothing gets a sane result.

| You set | Result |
| --- | --- |
| nothing | General logs: stdout/stderr (JSON off a terminal), `django_cfg` at `WARNING` (`DEBUG` when `debug=True`). Monitor events also go to a small rotating file `djangocfg/monitor.log` (10 MB x 5) in `/var/log/<app>` if writable, else the per-user state dir (`~/.local/state/<app>/log` on Linux, `~/Library/Logs/<app>` on macOS). If neither is writable: no file, events on stdout only, one warning |
| `logging.dir` or `DJANGO_CFG_LOG_DIR=/var/log/myapp` | also `django.log` there, and `djangocfg/monitor.log` in that directory (monitor events only in `monitor.log`, not twice) |

The directory is created when the first record is written, not at import. If it cannot be written, django-cfg logs one warning and keeps logging to stdout. Nothing is ever written inside the project tree, and `<cwd>/logs` is not used.

Precedence for every setting: explicit config (`logging.*`), then the env var, then the built-in default. `<app>` is the top package of `DJANGO_SETTINGS_MODULE`, else the working directory name, so projects on one machine do not share state.

## Configuration

```python
from django_cfg import DjangoConfig, DjangoLoggingConfig

class Config(DjangoConfig):
    logging: DjangoLoggingConfig = DjangoLoggingConfig(
        dir="/var/log/myapp",  # None = no general file; the monitor file uses the default chain
        level="INFO",          # django_cfg loggers; default WARNING, DEBUG with debug=True
        rotate_mb=10,          # rotate a file at this size; 0 = never (leave it to logrotate)
        backups=5,             # rotated files kept per log
        retain_days=14,        # boot prune: age of rotated files
    )
```

| Field | Type | Default | Env | Description |
| --- | --- | --- | --- | --- |
| `dir` | `str \| None` | `None` | `DJANGO_CFG_LOG_DIR` | Log directory (adds `django.log`, hosts the monitor file) |
| `level` | `str \| None` | `None` | `DJANGO_CFG_LOG_LEVEL` | Level of the `django_cfg` loggers |
| `format` | `"text" \| "json"` | json off a terminal | `DJANGO_CFG_LOG_FORMAT` | `json` is one object per line |
| `rotate_mb` | `int` | `10` | `DJANGO_CFG_LOG_ROTATE_MB` | Size at which a django-cfg log file rotates; `0` = never |
| `backups` | `int` | `5` | `DJANGO_CFG_LOG_BACKUPS` | Rotated files kept per log (`.1` ... `.N`) |
| `retain_days` | `int` | `14` | `DJANGO_CFG_LOG_RETAIN_DAYS` | Boot prune: rotated files older than this are deleted |

### Other environment variables

| Variable | Meaning |
| --- | --- |
| `DJANGO_CFG_LOG_DIR_MAX_BYTES` | Boot prune: the oldest rotated files go until the directory is under this. Default 500 MB; one warning if it is still over |
| `DJANGO_CFG_LOG_PRUNE` | `0` = no boot prune |
| `DJANGO_LOG_TO_TMP` | Deprecated and ignored. Logs one warning. The `/tmp/djangocfg/debug.log` mirror is gone |

`DJANGO_CFG_LOG_FILE`, `DJANGO_CFG_LOG_ROTATE`, `DJANGO_CFG_LOG_MAX_BYTES` and `DJANGO_CFG_LOG_KEEP_DAYS` no longer exist (use `DJANGO_CFG_LOG_DIR`, `..._ROTATE_MB`, `..._RETAIN_DAYS`). The config field `log_dir` is now `dir`.

<Callout type="info">
Rotation is by size and is safe with several workers: the rename happens under a
file lock and only if the file is still over the limit, so one worker rotates and the
others reopen. If `logrotate` already owns the file, set `rotate_mb=0`.
</Callout>

### Pruning

At boot, in a background thread and at most once a day per directory, django-cfg deletes
rotated files it wrote (`django.log.*`, `djangocfg/*`, and leftovers such as `apps.log`)
that are older than 14 days or beyond the backup count, then the oldest until the
directory is under 500 MB. A live file is never deleted. It never delays boot. If the
directory is still over the cap you get one warning naming the directory. By hand:

```bash
python manage.py log_prune                       # dry run: lists files and sizes
python manage.py log_prune --apply               # deletes
python manage.py log_prune --dir /var/log/myapp --days 7 --keep 3 --max-mb 200 --apply
```

### Removed fields

`enabled`, `file_enabled` and `file_rotation_days` were never read. `DjangoLoggingConfig` still accepts them (and ignores them with one warning) for one release. `django_cfg.LoggingConfig` is a deprecated no-op shim, removed in the next release.

## Upgrading from the `logs/` folder

django-cfg no longer writes to `./logs` and has no fallback or warning for it. A host that bind-mounts `/app/logs` can drop the mount: general logs are on stdout, and monitor events are in the per-user or `/var/log/<app>` file. To keep files in a known place, set `logging.dir` or `DJANGO_CFG_LOG_DIR` (outside the project tree). `python manage.py log_prune --dir /app/logs --apply` clears old dated files. See the [CHANGELOG](https://github.com/markolofsen/django-cfg/blob/main/CHANGELOG.md) for the full note.

## Public API

There is no logger factory; the module exports two plain functions and a constant.

### `sanitize_extra(extra)`

Prefixes any key in `extra` that conflicts with Python's reserved `LogRecord` attributes (e.g., `module`, `message`, `name`) with `ctx_` to prevent `KeyError`.

```python
from django_cfg.modules.django_logging import sanitize_extra

safe = sanitize_extra({"module": "myapp", "user_id": 42})
# {"ctx_module": "myapp", "user_id": 42}

logger.info("Event", extra=safe)
```

### `clean_old_logs(days=30, logs_dir=None)`

Deletes log files older than `days` from the log directory (default: the resolved one). Returns `{"deleted": 0, "bytes": 0, "error": ...}` when there is no log directory. Rotation and the boot prune already do this for django-cfg's own files; prefer `manage.py log_prune`.

```python
from django_cfg.modules.django_logging import clean_old_logs

stats = clean_old_logs(days=7)
# {"deleted": 12, "bytes": 45678, "human_readable": "0.04 MB"}
```

## Troubleshooting

### No log file is created

1. Without `logging.dir` / `DJANGO_CFG_LOG_DIR` there is **no `django.log` by design**; general logs are on stdout (`docker compose logs`). Only the monitor file `djangocfg/monitor.log` is written by default.
2. If even `monitor.log` is missing, django-cfg found no writable directory (`logging.dir`/env, `/var/log/<app>`, the per-user state dir) and logged **one warning**: `django-cfg found no writable directory for the monitor event log ...`. Monitor events are then on stdout only. A configured `dir` that cannot be written logs `cannot write to the configured log directory` and falls back to the defaults.

In a container the monitor events live in stdout only (the file is usually not written and `docker logs` holds them). Read them with the pipe form of `monitor_tail`, which skips banners, tracebacks and other loggers:

```bash
docker logs <container> 2>&1 | python manage.py monitor_tail --stdin [-n N] [--frontend] [--user ID] [--fingerprint HEX] [--session ID]
```
3. Fix: give the app user a writable directory and point to it, e.g. `DJANGO_CFG_LOG_DIR=/var/log/myapp` with `chown` to the container user, or mount a volume there. A default inside the project tree is never used.

```python
from django_cfg.core.utils.runtime_paths import resolve_log_dir, resolve_monitor_log_dir

print(resolve_log_dir())          # None = no django.log
print(resolve_monitor_log_dir())  # None = nothing writable, stdout only
```
