# Code generation

Topics travel through the same pipeline as the REST API: `make gen` reads them
from the OpenAPI document and writes metadata for the dedicated realtime
adapter alongside the target's generated TypeScript tree. Orval owns ordinary
REST operations; realtime transport remains a separate protocol adapter. There
is no hand-written topic string in the frontend when a typed topic builder is
available.

## `x-realtime` in the schema

The drf-spectacular hook `django_cfg.modules.django_realtime.openapi.postprocess_realtime` is in django-cfg's default `POSTPROCESSING_HOOKS`. It writes the registry into the document:

```json
"x-realtime": {"version": 1, "path": "/ws", "topics": [
  {"name": "orders:{order_id:int}", "params": [{"name": "order_id", "type": "int"}],
   "anonymous": false, "history": 100, "event": {"$ref": "#/components/schemas/OrderEvent"},
   "tags": ["orders"], "description": "Order status changes."}
]}
```

- Event models (and their nested models) become ordinary `components.schemas`, so they get zod schemas and types like any serializer.
- A topic's tag is its `group` (by default the declaring app), so the slicer puts it in that group's client.
- A group slice without topics has no `x-realtime` key at all (not `topics: []`), so its committed `openapi.json`/`openapi.yaml` does not change when another group gains a topic. Only the slices that carry topics have the key.
- A schema name that already holds a different schema stops generation (`SchemaCollision`): rename the event model. It is never overwritten.

## `realtime.ts`

Each group with topics gets a `realtime.ts` in its generated folder, beside `schemas/` and `hooks/`. A group without topics gets none (a stale file is removed). `OpenAPIConfig.generate_realtime` (on by default) controls it.

```ts
// AUTO-GENERATED by openapi_processor / ts.realtime (abridged: the RealtimeTopic type and segment() helper are omitted)
import { OrderEventSchema, type OrderEvent } from './schemas/OrderEvent';

export const REALTIME_PATH = "/ws";
export const REALTIME_PROTOCOL = 1;

/** `orders:{order_id:int}` (signed-in users, history 100). Order status changes. */
export function ordersTopic(params: { orderId: number }): RealtimeTopic<OrderEvent> {
  return {
    name: `orders:${segment("orders:{order_id:int}", "orderId", "int", params.orderId)}`,
    pattern: "orders:{order_id:int}",
    anonymous: false,
    schema: OrderEventSchema,
  };
}

/** Every topic of this group, by pattern. */
export const realtimeTopics = { "orders:{order_id:int}": { "builder": "ordersTopic", ... } } as const;
```

- **One builder per pattern**, named after its literal parts: `orders:{order_id:int}` → `ordersTopic({ orderId })`, `orders:{order_id:int}:items` → `ordersItemsTopic({ orderId })`, `demo.ping` → `demoPingTopic()`. When two patterns map to one name, the one with parameters gets them in its name (`ordersByOrderIdTopic`).
- Parameters are camelCase and typed: `{name:int}` is a `number`, `{name}` a `string`. A value that does not fit the segment syntax throws when the name is built.
- `schema` validates `msg.data`. A topic with the empty `Hint` event is typed `RealtimeTopic<RealtimeHint>`; without zod generation, `RealtimeTopic<unknown>` with `schema: null`.
- `RealtimeTopic<E>` is structural: `realtime.ts` never imports `@djangocfg/realtime`, and `useTopic` accepts it as is.

## Query-key invalidation

Mark the REST reads a topic makes stale, on a view, a viewset or an action:

```python
from django_cfg.modules.django_realtime import invalidated_by


@invalidated_by("orders.all")
class OrderViewSet(viewsets.ReadOnlyModelViewSet):

    @invalidated_by("orders:{order_id}")
    def retrieve(self, request, *args, **kwargs): ...
```

- Markers on the class and on an action add up. `@api_view` functions take it too.
- The pattern syntax is checked at import. Whether a declared topic of that shape exists is checked at schema generation: **a marker naming no declared topic stops generation** (`UnknownTopic`).
- A marker matches a declared topic by shape, so it may rename the parameters to match the URL: `invalidated_by("orders:{pk}")` matches `orders:{order_id:int}` and takes `pk` from the path.

django-cfg's schema class writes the markers as `x-realtime-invalidates` on each operation. The generated React Query query options associate the concrete topic names with their query keys:

```ts
const key = ["orders_retrieve", args, `orders:${String(args.path["order_id"])}`, "orders.all"] as const;
```

Each parameter comes from the **path parameter of the same name**. The `BaseApp` cache bridge watches every associated query while the hook is mounted and invalidates it on each message and gap. The generated REST client never imports `@djangocfg/realtime`, and the page has no realtime code. See [zero-code refresh](./frontend#zero-code-refresh-with-react-query).

## The `:` or `.` rule

The realtime bridge associates only topic names that contain `:` or `.`; a bare
word like `"me"` or `"list"` must never open a subscription. So a topic named
with neither (`topic("orders")`) cannot be used for query invalidation. Name
list topics with a dot: `orders.all`, `orders.list`.

## Warnings

| Where | Message | Fix |
|---|---|---|
| `make gen` log | `x-realtime-invalidates 'orders' is not tagged: a topic key part needs ':' or '.'` | Rename the topic (`orders.all`) or drop the marker |
| `make gen` log | `x-realtime-invalidates 'orders:{order_id}' is not tagged: no path parameter order_id` | Rename the marker's parameter to the URL's (`orders:{pk}`), or mark a route that has it |
| system check `django_cfg.W052` | `<view>: invalidated_by('orders') cannot tag a cache key` | The same as the first row, reported at startup |
| schema generation error | `GET /orders/{id}/: invalidated_by('orderz:{id}') names no declared topic` | Fix the name, or declare the topic |

An untaggable marker is skipped, not fatal: the key simply carries no tag, and the page does not refresh from that topic.

## Sender id in the auth runtime

The shared auth/runtime package also exports `setRealtimeCidProvider(provider)`.
The provider is kept in one page-wide slot, so installing it once covers every
generated target; their writes then carry `X-Realtime-Cid`. See [Frontend](./frontend#no-echo-for-your-own-writes).
