# Architecture

`django_mcp` contains two independent subsystems that share configuration and a global tool registry but otherwise operate completely separately.

## Two subsystems

### 1. MCP Protocol Server

Exposes Django data to external AI clients via the [Model Context Protocol](https://modelcontextprotocol.io/) JSON-RPC 2.0 wire format.

```
External AI client (Claude Desktop, Cursor, custom agent)
    │ POST /cfg/mcp/  (JSON-RPC 2.0, X-MCP-Access-Key header)
    ▼
MCPView (views.py)
    │
    ├── method: initialize      → handlers/initialize.py
    ├── method: tools/list      → handlers/tools.py → tool_registry.get_all_tools()
    ├── method: tools/call      → handlers/tools.py → tool.execute(context, args)
    └── method: resources/list  → handlers/resources.py
```

Every tool call receives an `MCPContext` (from `services/context.py`) carrying `user` (`AnonymousUser` by default, or the resolved [service account](/features/modules/django-mcp/configuration#service-accounts) when `service_username` is set), `session_key` (used for logging only — never an authorization input), the Django `request`, and the resolved `DjangoMCPModuleConfig`. There is no raw `access_key` field on the context; the key is only ever compared during authentication.

### 2. Admin Chat Agent

An LLM-powered chat interface embedded in the Django admin dashboard. It bypasses the MCP protocol entirely — it talks directly to the LLM via `django_llm` and uses MCP tools as plain Python callables.

```
Browser (Django admin /admin/)
    │ POST /cfg/mcp/agent/stream/
    │ body: {message, session_id, model}
    │ auth: Django session cookie + CSRF token
    ▼
MCPAgentStreamView (agents/api/views.py)
    │ validates auth, parses body
    │ builds AgentContext with all registered tools
    │ calls agent_runner.stream(message, context)
    ▼
MCPAgentRunner (agents/runner/runner.py)
    │
    │  ┌─────────────────────────────────────┐
    │  │  pydantic_ai.Agent over the MCP tools │
    │  │  (django_llm harness owns the loop)   │
    │  │                                       │
    │  │  each MCPTool → pydantic_ai.Tool via  │
    │  │  Tool.from_schema(input_schema)       │
    │  │  execute() runs in a thread           │
    │  └─────────────────────────────────────┘
    │       ↓
    │  final text answer
    ▼
StreamingHttpResponse (text/event-stream)
    ▼
Browser JS reads ReadableStream, renders tool calls + final answer
```

## Request lifecycle

`MCPView.post()` (the JSON-RPC endpoint) runs four steps for every request:

1. **Parse** the JSON-RPC 2.0 envelope. A malformed body returns a JSON-RPC parse error, not an HTTP-level 400.
2. **Authenticate and enforce.** `_authenticate()` resolves the caller (`AnonymousUser` or the configured service account) from `X-MCP-Access-Key`. Its return value is enforced immediately: if authentication fails and a key is required, the request is rejected with `401` before any handler runs.
3. **Derive a session key for logging only.** `_get_session_key()` computes a key from the request, but nothing is gated on it — see below.
4. **Route** to the JSON-RPC method handler (`initialize`, `tools/list`, `tools/call`, `resources/list`, ...) with a freshly built `MCPContext`.

<Callout type="info">
The transport is intentionally **stateless**, per the MCP Streamable HTTP spec. The server never issues an `Mcp-Session-Id` header, and nothing is gated on `_is_initialized` or any other session state — every `tools/call` is authenticated and authorized independently of whether `initialize` was ever called on that connection. Gating on session state without issuing a session ID previously broke every spec-compliant client: state was keyed on a hash of IP + User-Agent, so `initialize` and the following `tools/call` looked like different sessions whenever a client's requests didn't share one identical User-Agent — which is exactly what happens with real MCP clients spread across worker processes.
</Callout>

A `401` response carries `WWW-Authenticate: MCPAccessKey realm="mcp", header="X-MCP-Access-Key"` — a custom scheme, not `Bearer`. `Bearer` reads as OAuth 2.0 to MCP clients, which then go looking for `/.well-known/oauth-protected-resource` and fail in a way that's harder to diagnose than a plain 401.

## Profile routing

A [profile](/features/modules/django-mcp/configuration#profiles) is resolved from **the URL the request arrived on**, never from a header, and it is what step 2 and step 4 above read. `MCPView.as_view(profile="public")` binds a view to one; the plain `MCPView` falls back to the synthesised `default` profile, which is what every URL registered before profiles existed resolves to.

Profile routes are registered by `django_cfg.apps.urls`, not by the project — a profile that exists in the config but on no URL is invisible in the worst way: the config reads correct, the tool filter works, and the endpoint 404s. `urls.profile_urlpatterns()` builds them **lazily**, behind a `URLResolver` whose URLconf is resolved on first use. The module is imported while settings are still being built, when the MCP config does not yet exist; reading it at import time yields `None` and silently registers nothing, and an empty list is a perfectly valid URLconf, so the routes simply would not be there.

Both `MCPView` and `MCPInfoView` read the profile the same way, and take the access key from the same object — the profile when one resolves, the flat config otherwise. Taking the gate from one and the key from the other would let a profile be gated by one key and unlocked by another.

## Shared tool registry

Both subsystems use the same global `MCPToolRegistry` instance from `tools/base.py`. Tools are registered once in `handlers/tools.py` at import time, which is triggered by `auto_loader.py` inside `AppConfig.ready()`. After Django startup, both `MCPView` and `MCPAgentRunner` pull from the same registry — adding a tool makes it available in both contexts simultaneously.


## LLM integration

The admin chat agent builds a `pydantic_ai.Agent` and delegates the agentic loop to `django_llm`'s harness, which resolves the provider (OpenRouter first). `MCPAgentRunner` keeps its public surface — `run(...) -> str` and `stream(...) -> Generator[dict]` — so callers are unaffected by that.

Each registered `MCPTool` is wrapped as a `pydantic_ai.Tool`: `input_schema` becomes the parameter schema via `Tool.from_schema`, and `execute()` runs in a thread (`sync_to_async`), because it is synchronous and may touch the ORM — a tool coroutine that blocked on the database would stall the event loop the streaming path drives. A tool that raises returns its error as the tool result rather than raising into the loop, so the model can read the failure and recover.

The model is resolved in this priority order:

1. `model` field in the request body (explicit per-request override)
2. `mcp_config.llm_model` from `DjangoMCPModuleConfig` (default: `"openai/gpt-4.1-nano"`)
3. Hard fallback: `"openai/gpt-4o-mini"`

## Security boundaries

| Path | Auth mechanism | Who can access |
|------|---------------|----------------|
| `POST /cfg/mcp/` | `X-MCP-Access-Key` header | External MCP clients with static key |
| `POST /cfg/mcp/agent/` | `X-MCP-Access-Key` header | Programmatic agents with static key |
| `POST /cfg/mcp/agent/stream/` | Django session + CSRF token | Authenticated users (superuser UI gate) |
| `GET /cfg/mcp/info/` | `X-MCP-Access-Key` header, unless `public_info=True` | Anyone, if `public_info=True` or no `access_key` is configured — otherwise the same holders as `POST /cfg/mcp/` |
| `POST <profile.path>` | Whatever that profile's `access` says | Callers of that profile — see [Profiles](/features/modules/django-mcp/configuration#profiles) |
| `GET <profile.path>info/` | Follows that profile's `public_info` | Anyone on an anonymous profile; keyholders otherwise |

The streaming endpoint (`agent/stream/`) checks `request.user.is_authenticated` and requires a valid CSRF token. The admin template wraps the chat UI in `{% if user.is_superuser %}`, so only superusers see it in the admin panel.

<Callout type="warning">
`/info/` returning tool names, descriptions, and full input schemas used to be unconditional — a capability map for the whole app, handed to anyone. As of `public_info` (default `False`), it now follows the JSON-RPC endpoint's gating: if `access_key` is set, `/info/` requires it too. Set `public_info=True` only if you want that listing to stay public regardless.
</Callout>
